# NutriTrack AI — Outcome ToDo

This project has no native Webdev ToDo tool, so this file tracks the approved plan. All outcomes below are complete based on the implementation and review evidence recorded in the project history. The frontend remains intentionally independent of a backend and does not claim that scanner AI is connected.

## [x] Responsive shell, design system, and navigation

Create a premium, clean, friendly health-tech design with modern readable hierarchy; soft shadows and restrained borders; 16–24px card radii; generous spacing; Lucide React icons consistently and no emoji interface icons; custom SVG illustrations only where useful; no excessive gradients, animation, or dashboard clutter; accessible contrast, visible focus, keyboard navigation, and semantic HTML; loading skeletons, empty/error states, and success feedback. Use the specified design tokens: forest green `#244C3A`, sage `#A8C5A0`, background `#F8F6EF`, card white `#FFFFFF`, coral `#F08A70`, text `#202821`, secondary text `#70776F`, borders `#E5E8DF`, success `#3C8B62`, warning `#E4A34A`, and error `#D9534F`. Create a responsive desktop sidebar, mobile top bar, fixed mobile bottom navigation with safe-area padding, user profile menu, notification area, page title/contextual actions, global toast notifications, reusable modal and confirmation dialog, and consistent loading/empty-state components. Navigation must include Dashboard, Food Diary, AI Food Scanner, Nutrition Analytics, Workouts, Weight & Goals, and Profile & Settings, with visually clear active states. Support phones around 320px, standard/large phones, tablets, laptops, and wide desktop screens; keep mobile small-phone content one column and larger content responsive; use a collapsible desktop sidebar; ensure no horizontal overflow, comfortable touch targets, stacked chart legends/forms on narrow screens, safely responsive tables, viewport-fitting internally scrollable dialogs, one-hand scanner/manual logging, and device safe-area/browser-viewport behavior. Test every page at 320px, 360px, 390px, and 430px widths, as well as the brief's 375px, 768px, 1024px, and desktop widths. Add Food and Scan Food actions must be easy to reach with one hand.

## [x] Dashboard and nutrition summaries

Build a daily dashboard with greeting and selected date; daily calorie target; calories consumed; calories remaining or exceeded; an animated circular calorie progress indicator; protein, carbohydrates, fat, and fiber progress cards; breakfast, lunch, snacks, and dinner sections; food entries with serving quantity and nutrition; quick actions for Scan Food, Add Food, Log Workout, and Log Weight; optional daily water tracking; today's activity summary; recent meals; a seven-day calorie trend chart; and clear empty states for users who have not logged meals. Calculate `remaining = daily target - calories consumed`: when positive, show calories remaining; when negative, show how far the target was exceeded; never display negative remaining calories as available calories. Use realistic development demo data and clearly separate/label it from real user records.

## [x] Food diary and nutrition calculations

Implement a working frontend diary with date navigation and jump-to-date calendar; separate breakfast, lunch, snacks, and dinner sections; add, edit, duplicate, and delete entries; food-name search; quantity and serving-unit selectors; calories, protein, carbohydrates, fat, and fiber display; meal subtotals and daily total; destructive-action confirmation; access to old diary dates; and a helpful empty state. Manual entry must collect food name, quantity, unit, calories, protein, carbohydrates, fat, fiber, meal category, and optional notes; validate numeric values and reject negative quantities or nutrition values. Calculate nutrition totals correctly. Every saved entry must carry its own nutrition snapshot (calories, protein, carbohydrates, fat, and fiber) so later changes to a reference food cannot silently rewrite historical diary values.

## [x] AI food scanner and privacy-safe review/save

Provide three scanner inputs: open the device camera where supported, upload a food image, or type a meal description such as “4 idli and 1 tea.” For images, show a preview; allow replacing/removing the selected image; show file validation and upload progress; explain privacy; keep images only in memory; do not save them to the diary or browser storage and do not persist them in localStorage or IndexedDB; revoke temporary object URLs when previews are removed, replaced, or no longer needed. Never claim an image was analyzed when no real AI service is connected. If there is no backend, clearly label mock analysis mode and keep the UI ready for a future real API. The results interface must show detected foods, editable portion sizes, estimated calories, protein, carbohydrates, fat, and fiber, confidence/uncertainty when available, warnings when oil/sugar/ingredients/serving size are uncertain, and controls to edit/remove/add detected foods. Review & Save must require user confirmation before saving analysis as a diary entry.

## [x] Nutrition analytics

Build daily, weekly, monthly, and yearly views. Include calories consumed versus target; protein, carbohydrate, fat, and fiber trends; average daily intake; days above/below target; consistency and logging statistics; weight trend chart; date-range filters; helpful no-data states; and responsive charts with readable axes, tooltips, legends, and accessible labels. Do not fabricate historical records as real data; clearly label demo data.

## [x] Goals, weight, profile, and settings

Create forms for date of birth, automatically calculated age, height and measurement unit, current weight, biological sex (used only if needed for the selected calorie-estimation formula), activity level, goal (weight loss, maintenance, weight gain, or muscle building), target weight, and preferred measurement units. Display estimated maintenance calories and suggested daily calorie targets; explain these are estimates, not exact measurements or medical advice. Allow goal updates over time with effective dates so historic analytics retain targets applicable to each period; never silently overwrite historical goal data. Include profile editing, unit preferences, privacy settings, and account settings.

## [x] Workouts and calorie accounting

Create strength-training sessions; workout split selection (chest/triceps, back/biceps, legs, or custom); exercise name, sets, repetitions, weight lifted, and notes; cardio type, duration, and optional distance; estimated exercise calories clearly labelled as estimates; workout history and progress charts; and add/edit/delete workout sessions. Keep estimated exercise calories distinct from daily maintenance calories, make calorie-accounting rules clear, and avoid double-counting exercise calories when the maintenance estimate already includes normal activity.

## [x] Typed frontend architecture, demo adapter, quality, and handoff

Use React 18+ with TypeScript, Vite, Tailwind CSS, React Router, lucide-react, Recharts, Framer Motion, React Hook Form, Zod, and date-fns at compatible stable versions. Use reusable, well-typed components and clear modules for app, components/layout/navigation/ui/charts/food, pages, dashboard/diary/scanner/analytics/workouts/goals/profile features, hooks, services, types, utils, mocks, and styles. Define typed models for UserProfile, NutritionGoal, FoodEntry, Meal, FoodAnalysis, WorkoutSession, Exercise, CardioSession, WeightLog, and DailyNutritionSummary. Provide a typed API service layer and future backend-base-URL environment support so REST APIs can be connected later without rewriting page components; do not put AI API keys or database credentials in frontend environment variables. Keep mock repository/development-only local data replaceable with real REST services and do not represent mock persistence as secure production storage. Before backend integration, frontend navigation, date/category selection, food CRUD, nutrition/calorie calculations, goal/profile validation, workout creation/editing, chart filtering, modal open/close, responsive navigation, and toast feedback must work. Include error handling/loading states, avoid duplicated UI and oversized components, ensure no broken buttons/dead links, TypeScript errors, missing icon imports, horizontal overflow, API secrets in frontend code, false AI claims, or image persistence. Add useful README setup instructions. Finish the frontend and responsive/accessibility review before any backend development.
